## 1. 需求 1：检测段数据从哪来

### 1.1 现在的检测段有什么、缺什么

检测段（每条焊缝一次）在 KRL 侧计算并写入以下全局量（见 `$config.dat:948-1000`）：

| KRL 变量 | 含义 | 现在能传到上位机吗 |
|---|---|---|
| `Measure_Height<k>` | 焊缝高度（mm）= `GetHFZ()` | ❌ |
| `Baseheight<k>` | 基材高度（浮动模块到位值）= `InitLen + LENGTH` | ❌ |
| `Cuobian<k>` | 错边量（mm）= `LV1 − LV3` | ❌ |
| `TIMES<k>` | 计划打磨轮次 = `MOD(LENGTH/Ofs)` | ❌ |
| `InitLen<k>` | 力控起点（`ESpos`） | ✅（`MonRef=ESpos`，10-10 已落地） |
| 焊缝号 k | — | ✅（`PassNo = -(k)`，10-10 已落地） |

### 1.2 为什么"不加字段"办不到（推导）

关键在 KRL 的检测公式：

```
InitLen  = FinalPos − ((LV1+LV3)/2 − AVG_k)*100 − GZoffset_k − LENGTH_k      ← 上传为 EsPos
Baseheight_k = InitLen + LENGTH_k
Cuobian_k    = LV1 − LV3
Measure_Height_k = LENGTH_k / 100
```

上位机已知：`EsPos`、以及每条焊缝的常量 `FinalPos / AVG_k / GZoffset_k`。

```
EsPos = C_k − M*100 − LENGTH        （C_k 已知；M=(LV1+LV3)/2，LENGTH 未知）
```

**一个方程，两个未知数（`M`、`LENGTH`）→ 无法分离**，因此：

- 焊缝高度（∝`LENGTH`）**拿不到**；
- 基材高度（=`EsPos + LENGTH`）**拿不到**；
- 错边量（=`LV1−LV3`）需要 `LV1`、`LV3` 各自的值，**更拿不到**。

### 1.3 三种字段方案，按"KRL 改动量"排序

| 方案 | 新增字段 | KRL 改动 | 能得到 | 评价 |
|---|---|---|---|---|
| **A（推荐）** | `WeldH`(REAL) `BaseH`(INT) `Misalign`(REAL) `Rounds`(INT) | 与 `krl/KRL_update_20261014/` **完全一致**（已有现成改动） | 4 项全部直接得到 | 改动已写好，只需落地 + 上位机加解析 |
| **B（精简）** | 仅 `WeldH` + `Misalign` | 只需 2 个 `<ELEMENT>` + 2 行 `EKI_Set` | 4 项全部可得（`BaseH = EsPos + WeldH*100`；`Rounds = floor(WeldH*100/Ofs)`） | KRL 改动减半；`Rounds` 需在上位机复刻 `MOD()` 截断语义，需单测对齐 |
| **C（不推荐）** | 仅 `WeldH` | 1 个字段 | 错边量缺失 | 需求 1 不满足 |

> 说明：`ECM/EsPos` 上传的是 `MonRef` 而不是 `ESpos`，所以检测段的 `EsPos` 就是 `InitLen`——这是方案 B 能推算 `BaseH` 的基础，前提是 KRL 侧保留 10-10 那批 `MonRef = ESpos` 改动。

**结论：需求 1 的最小必要改动 = 落地检测值上传（方案 A 或 B）+ 上位机 `Sample` 增加对应字段。**

### 1.4 `PassNo` 能不能直接当焊缝号用

**可以，而且现在就是这么用的**（`src/station.cpp:decodePassNo()`）。但有 3 条必须知道的约束：

1. **正数 `PassNo` 不自带焊缝号**。`PassNo = 5` 只表示"第 5 道"，归属哪条焊缝要靠**紧邻的前一个负标记**（`-(k)` / `-(10+k)` / `-(100+k)` / `-(110+k)`）。现有 `SeamTracker::curSeam` 就是"最近一次负标记"的记忆，逻辑正确。
2. **因此"打磨段开头必须有一次负标记"**。粗磨程序有（`PassNo = -(10+k)`）；细磨程序**当前没有** → 细磨的打磨数据无法归属焊缝。落地 100 段标记即可解决。
3. **`PassNo` 里只有编号，没有数值**。4 个检测值必须走独立字段，不能塞进 `PassNo`（`PassNo` 是 32 位有符号 INT，硬塞会破坏现有的阶段/工序语义）。

## 2. 数据模型改造（所有需求的地基）

### 2.1 现状

`DataGroup` = 一次 `RecordOn` 周期；`Pass` = 正数 `PassNo` 区间；`SeamStat` = 焊缝统计（含 `detectEs`）。**缺一层"段"的概念**，导致"把某条焊缝的检测段单独画出来"这件事没有直接数据支撑。

### 2.2 新增：段表（Segment）

由 `PassNo` 序列一次性切出（实时记录与 CSV 载入共用同一实现）：

```
struct Segment {
    SegKind  kind;    // Detect / Pass(打磨道) / GrindGap / Transfer / Finish
    Craft    craft;   // Rough(粗磨) / Fine(细磨) / Unknown
    int      seam;    // 1..8（0 = 未归属）
    int      passNo;  // 正数道次号；非打磨段 = 0
    bool     retry;   // 补充打磨
    double   t0, t1;  // 组内相对时间
    int      i0, i1;  // 点下标区间（含）
};
```

`PassNo → (kind, craft, seam)` 的唯一映射（在现有 `decodePassNo()` 上扩展）：

| PassNo | kind | craft | seam |
|---|---|---|---|
| `n > 0` | Pass | 由**紧邻前一个负标记**决定 | 同上 |
| `0` | Gap / 未标记 | 同上（未知则 Unknown） | 同上 |
| `-(k)` | Detect | Rough | k |
| `-(10+k)` | GrindGap | Rough | k |
| `-(20+k)` | Transfer | Rough | k |
| `-(100+k)` | Detect | Fine | k |
| `-(110+k)` | GrindGap | Fine | k |
| `-(120+k)` | Transfer | Fine | k |
| `-99` / `-199` | Finish | Rough / Fine | 0 |

> 这是**唯一让"粗磨 / 细磨分离"成立的机制**，也是需求 2、4 的前提。

### 2.3 新增：检测快照（DetectSnapshot）

在 `Detect` 段内**持续更新**、段末自然定格（比"只取最后一帧"更抗丢帧）：

```
struct DetectSnapshot {
    int    seam = 0;
    bool   valid = false;
    double weldH = 0;      // ECM/WeldH  (mm)
    int    baseH = 0;      // ECM/BaseH  (位置量)
    double misalign = 0;   // ECM/Misalign (mm, 可负)
    int    rounds = 0;     // ECM/Rounds（计划轮次）
    int    esBase = 0;     // 检测段最后的 EsPos（= InitLen，现有 detectEs，做交叉校验）
    int    normalN = 0;    // 实际完成正常道次（打磨段统计）
    int    retryN = 0;     // 实际补充打磨次数
    double t0 = 0, t1 = 0;
};
```

每条焊缝一个快照（`SeamStat` 扩展）。界面顶部只要读这个结构即可显示"焊缝 k：高度 / 基材 / 错边 / 计划轮次 / 实际道次"。

### 2.4 新增：件（Part）层

```
Part {
    int      id;            // 件号（见 §3.4）
    QString  label;         // 显示名，如 "件 0007"
    QDateTime t0, t1;
    QVector<int> cycles;    // 属于本件的 RecordOn 周期在内存中的索引
    // 派生：每条焊缝的 DetectSnapshot + 段索引
}
```

**三层结构：`Part → Cycle(RecordOn) → Segment`**，需求 1/2/4/5 全部挂在这三层上。

## 3. 自动分件（"换料件软件能识别出来"）

### 3.1 客观限制

协议里**没有件号、没有程序号**，所以"新件开始"只能由以下信号推断：`RecordOn` 边沿、焊缝号序列、时间间隔、以及预留编码（`-99`/`-199`）。

### 3.2 四种分件规则（做成可配置，默认 R1）

| 规则 | 判据 | 优点 | 失效场景 |
|---|---|---|---|
| **R1 焊缝号回绕**（推荐默认） | 同一工序内出现"焊缝号回绕到更小值"或"从 8 之后回到 1" ⇒ 新件 | 不需要改 KRL；对"Part1→Part2 顺序生产"天然正确（1..4→5..8 单调递增不误判） | 若一件内粗磨跑完 1–8 后再跑细磨 1–8，回绕会**误判为新件**（需配合 R1' 见下） |
| **R1' 回绕 + 工序区分** | 仅当**同一工序内**回绕才算新件 | 解决"粗→细"误判 | 依赖 §1.3 的工序标记落地 |
| **R2 显式件标记** | KRL 每件开始打一个预留编码（如 `PassNo = -200`）⇒ 新件 | 最可靠、无歧义 | 需要 KRL 改 1 行；需占用一个预留编码 |
| **R3 手工 + 超时兜底** | 点"新件"按钮；或超过 N 分钟（可设 10/30/60）无数据 ⇒ 新件 | 零依赖，兜底 | 纯手工不够自动 |
| **R4 一周期一件** | 一次 `RecordOn` = 一件（即现状语义） | 最简单，立即可用 | 与"一件含粗磨+细磨"的真实情况不符 |

**推荐落地组合**：默认 **R1/R1'**（自动） + **R3**（兜底按钮与超时），并把 **R2** 作为"未来 KRL 侧配合后切换"的目标。同时保留 **R4** 供现场选择。

> 关键待确认：**"一件"到底等于什么？** 见 §9 问题 1。这个答案直接决定默认规则。

### 11.1 线上崩溃修复（2026-10-15）

**现象**：连续生产跑到第 5 件左右，程序在监控过程中直接退出（无对话框）。

**根因（本方案的回归）**：为支持连续生产把 `MAX_GROUPS` 从 4 提到 64，但
`MainWindow::nextPaletteIdx()` 的取值域跟着变成了 `0..MAX_GROUPS-1`，而
`theme::GROUP_PALETTES` 只有 4 个元素 —— **第 5 个数据组起就在读数组外的内存**；
`Palette` 的第一个成员是 `QString`，越界读到的野 `QString` 在拷贝时会解引用非法指针。
是否立刻崩溃取决于链接器布局（Debug / Release 不同），所以表现为"偶发、跑一阵才崩"。

**修复**：

| 位置 | 改动 |
|---|---|
| `src/theme.h` | 新增 `PALETTE_COUNT` 与 `theme::paletteOf(int)`，下标自动回绕；**取配色只有这一个入口** |
| `src/mainwindow.cpp` | `nextPaletteIdx()` 只在 `PALETTE_COUNT` 范围内挑空位（组数超过 4 时颜色复用，是预期行为） |
| 全部 13 处调用点 | `GROUP_PALETTES[g->paletteIdx]` → `paletteOf(g->paletteIdx)` |
| `tests/tst_theme.cpp`（新增） | 断言 `paletteOf(i)` 返回的引用**地址必须落在数组内**（对 `-8..256` 与 `0..MAX_GROUPS-1` 全量扫描）。这是确定性判据，不依赖布局运气 |

验证：把修复临时回退成旧写法 → `tst_theme` **失败**（`paletteOf(4)` 越界、第 5 组越界）；
恢复修复 → 9/9 测试通过，并用 10 件数据（越过 `keepGroups=8` 的内存回收边界）端到端跑通无崩溃。

### 11.2 启动可观测性（2026-08-15 同日）

| 改动 | 目的 |
|---|---|
| 工具栏常驻**连接指示灯**（监听失败 / 等待连接 + 本机 IP / KUKA 已连接） | 区分"没监听"与"KUKA 没连过来"，这两类问题的处理完全不同 |
| 监听失败不再弹模态框，改为常驻红字 + 状态栏 | 监控程序要能无人值守启动；模态框会让人以为程序卡死 |
| 每次启动追加一行 `KRLmonitor.log`（exe 同目录） | 记录监听结果、错误原因、本机 IP、关键配置，现场排查先看这一行 |
| `--arm` 命令行参数 | 忽略设置强制进入监听，便于做开机自启/快捷方式 |

**单位约定（务必与现场一致）**：`$config.dat` 把这 4 个量声明为 `INT`，其中 `WeldH/Misalign` 是 **µm**，
因此界面显示时除以 1000 得 mm；`BaseH` 是位置量整数，`Rounds` 是轮次整数。
若现场改成 `REAL`（mm）+ `EKI_SetReal`，只需把 `src/mainwindow.cpp:refreshSeamDetail()` 里的换算去掉。

### 3.3 分件状态机（示意）

```
每帧: PassNo → decodePassNo() → (phase, craft, seam)
  ├─ phase==Detect && craft==CraftOf(currentPart) && seam < lastSeamThisCraft
  │        ⇒ 触发"新件"（R1'）
  ├─ 距上一帧 > timeout
  │        ⇒ 触发"新件"（R3）
  └─ RecordOn 上升沿 ⇒ 开新 cycle，挂到 currentPart
RecordOn 下降沿 ⇒ 封 cycle；若本 cycle 已"完成一次单面打磨"
                 ⇒ 触发自动存档（§6.4），并把该件从内存移出（§7.2）
```

### 3.4 件号生成与跨重启

- 件号 = `时间戳(到秒) + 当日序号`，落盘文件名里也带时间（到分钟），保证唯一且人可读；
- 软件重启后从存档目录扫描已有文件名，**续上当日序号**；
- 件号一旦分配即写入存档元数据，事后可对号。

### 4.2 视图模式（工具栏/焊缝栏切换）

| 模式 | 内容 |
|---|---|
| **整件** | 现状：整条时间轴，焊缝底色带 + 道次分割线（保留） |
| **按焊缝** | 只画选中焊缝的点；其余置灰或不画 |
| **按阶段** | `检测段` 与 `打磨段` 视觉区分：打磨段实线 + 段底着色，检测段虚线/浅底（或上下分栏） |
| **按工序** | 粗磨 / 细磨 分组切换 |
| **叠道对比** | 由现有 `drawOverlay` 扩展：叠道键从"道次出现顺序"改为 `(焊缝, 工序, 道次)`，可把同一条焊缝的 1..n 道叠在一起比较 |
| **段拼接（压缩空移）** | 🔸可选：把选中段首尾相接，隐藏工位间空移与返回段，便于同尺度比较。注意此时 X 轴不再是"真实时间"，需在轴上标注 |

### 4.3 检测段曲线怎么画

检测段本身只有 4~5 个采样点（Pk1→Pk8→Pk2→Pk3，约 1 秒），画在曲线里几乎是个点。因此检测数据的**主要呈现是数值卡片**（§5.3），曲线视图里用一条竖线 + 标注把检测时刻标出来即可。

## 5. 需求 3：界面调整

### 5.1 焊缝栏（紧凑化）

```
现状：每焊缝一张大卡片（标题/阶段/遍数/次数/实时值）占满一行
改为：一排小 chip，只显示序号与状态

  [①][②][③][④][⑤][⑥][⑦][⑧]        ← 每格 ≈ 34×26 px
   ●  = 本件已出现；○ = 未出现        ← 用底色/圆点区分
   高亮 = 当前正在打磨
   选中/未选中 = 点击切换（默认全选）
```

- 默认**全部选中**；再次点击取消；提供"全选/全不选"两个快捷操作。
- 选中集合 = 图表的焊缝过滤器（需求 4）。
- 每条焊缝保留一个固定配色，图例与 chip 同色（现有 `paletteIdx` 机制复用）。
- 卡片的原有信息（阶段、遍数、次数、实时值）移到**数值栏一行**，不占版面。

### 5.2 版面对比（空间分配）

```
现状：  [工具栏] [焊缝卡片行：高] [图表：剩余] [数值栏]
改为：  [工具栏(含焊缝 chip + 视图模式)] [图表：占绝对主体] [数值栏(含当前焊缝详情)]
```

### 5.3 数值栏（承载原卡片信息）


## 6. 需求 5：保存机制

### 6.1 文件格式 `.ecmb`（ECM Binary）

```
┌ 头 ─────────────────────────────────────────────┐
│ magic "ECMB" (4B) | version u16 | flags u16      │  flags: bit0=zlib压缩, bit1=混淆/加密
│ pointCount u32 | segCount u32 | headerLen u32    │
├ 元数据（UTF-8 JSON，便于向后兼容扩展）──────────┤
│ 件号/时间/工序/焊缝列表/每焊缝 DetectSnapshot/     │
│ 记录时的关键 KRL 参数快照（Ofs/FinalPos/AVG…）     │
├ 段表 segCount × { i0 u32, i1 u32, kind u8,        │
│                   craft u8, seam u8, passNo i16 }│
├ 数据块（列式：每列连续存放，利于压缩）────────────┤
│ dt u16(ms) | pos i32 | force i16 | passNo i16 | es i32 │
├ CRC32 ──────────────────────────────────────────┤
```

要点：

- **列式存储**（同一字段连续）+ `dt` 用毫秒增量，压缩率明显优于行式；
- 段表落盘 ⇒ 打开时不必重算分段，也不会因算法调整而改变历史文件语义（**格式版本号**保证兼容）；
- `flags` 预留"将来换算法"的空间；
- **CSV 继续保留**（导出用），二进制作为主格式。

### 6.2 体积估算

以 100 Hz 采样、5 列数据为例：

| 形式 | 每点 | 每小时 | 相对 CSV |
|---|---|---|---|
| 现有 CSV（6 列文本） | ≈ 34 B | ≈ 12 MB | 1× |
| 二进制行式（i32×3 + i16×2 + u16） | 14 B | ≈ 5 MB | ≈ 1/2.4 |
| 二进制列式 + zlib | ≈ 2–4 B | ≈ 1–1.5 MB | **≈ 1/10** |
| 再加 delta-varint 编码 pos/es | ≈ 1.5–3 B | ≈ 0.7–1 MB | ≈ 1/15 |

即：**"体积更小的二进制文件"完全可行，压缩后约为 CSV 的 1/10。**

### 6.3 "由本文件解密打开"——三档强度

| 档 | 做法 | 保密强度 | 依赖 |
|---|---|---|---|
| 1 混淆 | 固定密钥 XOR / 字节置换 + zlib | 低（防"文本编辑器直接看/误改"） | 无 |
| **2 流加密**（推荐） | zlib + 自实现 RC4/ChaCha20 或 XOR-流 + CRC | 中（防一般工具打开） | 无（自实现 ~100 行） |
| 3 强加密 | AES-128-CTR + HMAC | 高 | Qt **无内置 AES**：需自实现（~200 行）或引入单文件库（如 tiny-AES-c，public domain） |

> 结论：**能做，但"加密"不是 Qt 开箱能力**。若只是"不想让人随便打开"，档 2 足够且零依赖；若要求抗破解需上档 3。
> 加密只影响"本软件打开"，不影响"本软件导出 CSV"（导出走明文，便于 Excel 使用）。

### 6.4 自动存储与命名

```
触发点：一次"单面打磨"完成 → 封 cycle 时判定（可配置为"每周期"或"每件"）
目录  ：可设置（默认 <我的文档>\KRLmonitor\<日期>\）
命名  ：<时间到分钟>_<件号>_<工序>_<焊缝范围>.ecmb
        例：2026-10-14_16-52_件0007_粗磨_1-8.ecmb
```

- 命名规则做成模板串（设置项），默认 `{time}_{part}_{craft}_{seams}`；
- 同名冲突追加 `-2`、`-3`；
- 存储失败（无权限/无空间）**必须**在状态栏与日志里明确报错，且**不丢内存数据**。

## 7. 整体愿景：打开即通讯 + 长期运行 + 自动识别件

### 7.1 打开即通讯

- 启动时自动 `listen(65002)`（现已有）+ **自动进入监听（auto-arm）**；
- 设置项可关闭自动监听（调试用）；
- 启动时若已有存档目录，显示"今日已存档 N 件"，件号续编。

### 7.2 长期运行：内存策略（替代现在的 4 组上限）

现状对"长期运行"有两处硬阻断（`MAX_GROUPS = 4` 静默丢数据、默认"完成后暂停"会停止采集）必须改造：

| 现状 | 改为 |
|---|---|
| `MAX_GROUPS = 4`，第 5 件**静默丢数据** | **内存只保留"当前件 + 最近 N 件"（N 可设，默认 3）**；更早的件落盘后释放。丢弃/回收必须在状态栏明确提示 |
| 默认"完成后暂停"（`m_autoPause=true`） | 默认**不暂停**（连续跑）；"完成后暂停"降级为"仅冻结视图、不影响采集"或保留为可选 |

### 7.3 断线兜底（必做）

`TcpServer::onDisconnected()` 目前只改状态文字，不通知记录层 → 断线重连会把两件并成一组。改造：

```
断线 ⇒ 若正在记录：强制封 cycle，标记该 cycle "可能不完整"；
       并 markPrevUnknown()，使重连后的第一个边沿一定新建周期。
```

### 7.4 原始数据是否要"永远不丢"

可选增强：追加一个**原始帧落盘**（可选开关），即把收到的每一帧按二进制追加到当日文件。这样即使上位机分件规则判断错了，原始数据还在，可事后重放重新分件。**强烈建议开启**，因为分件规则依赖现场行为，事后重算是最稳的保险。

## 9. 必须先确认的问题（答案会改动方案）

1. **"一件"的定义**：一次程序运行（4 条焊缝）= 一件？还是"粗磨 1–8 + 细磨 1–8"合起来 = 一件？
   → 决定默认分件规则（R1 还是 R1' 还是 R2）与自动存档的触发点。
2. **"一次单面打磨"是什么粒度**：一次 `RecordOn` 周期？还是一件？是否一件有两个面（正面/反面）需要分别存储？
3. **是否接受 KRL 侧改动**：方案 A（4 字段，改动已写好）还是 B（2 字段）？如果都接受不了，需求 1 只能降级为"只有基准高度"。
4. **细磨是否也要监控**：若需要，细磨程序必须补 `-(100+k)`/`-(110+k)` 标记（10-14 包已有）；不补的话细磨数据无法归属焊缝，也没有工序区分。
5. **"打磨轮次"要哪个值**：计划轮次（`TIMES`，KRL 给）还是实际完成道次（上位机统计）？建议两个都显示。
6. **加密强度**：档 2（零依赖混淆）够不够？要求抗破解才上档 3（需引入/自实现 AES）。
7. **原始帧落盘**（§7.4）是否开启？会额外占用磁盘（约 100 B/帧 ≈ 36 MB/小时，压缩后 ~5 MB/小时）。
8. **现场是否每件都重新执行程序**（决定 `RecordOn` 边沿是否可靠）——这一点不确认，任何自动分件都可能在现场行为下失效。

## 10. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| KRL 侧字段没落地 | 需求 1 降级、需求 4 的检测曲线无内容 | 先做 S1 的解析与快照，字段缺失时显示"—"并明确提示，不静默 |

| 现场不是每件重新执行程序 | 自动分件失效 | §7.4 原始帧落盘 + 事后重算；或改 KRL 加件标记（R2） |

| 二进制格式将来变更 | 旧文件读不出 | 格式版本号 + 元数据 JSON + 段表落盘 + 单测覆盖往返 |
